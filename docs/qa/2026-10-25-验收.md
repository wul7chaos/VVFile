## 12. 下拉刷新改为自绘手势 + 内部存储容量修正（2026-10-25）

### 12.1 下拉刷新只在上方生效的问题

现象：条目少的目录（列表不可滚动）里，按在空白处往下拖完全不刷新，只有列表能滚动时才偶尔生效。

原因：`PullToRefreshBox` 依赖子级 scrollable 的 nested scroll 事件。列表内容不足一屏时 LazyColumn
不产生滚动分发，父级收不到手势；顺带还出现过指示器卡在「释放刷新」不消失。

改法：不再用 `PullToRefreshBox`，在窗格内容区自己挂 `pointerInput` 观察拖拽：

- `awaitEachGesture` + `PointerEventPass.Final`，**只观察不消费**，列表原有滚动/点击/滑选全部不受影响；
- 仅当 `listState.canScrollBackward == false`（已到顶）时累计向下位移，向上滑立即清零；
- 松手时 `sumY >= 90.dp` 且竖直位移大于水平位移才触发 `onPullRefresh()`；
- 提示块由 `pullOffset / threshold` 驱动，松手即归零，不会卡住。

| 项 | 结果 | 证据 |
| --- | --- | --- |
| 空白处下拉刷新（2 个文件的目录） | 通过 | 外部建 `e.txt` 后按在空白区下拉，`4 → 5` 个文件 |
| 只刷新被拖动的窗格 | 通过 | 同图右窗格仍是 4 个文件 |
| 长列表下拉仍可用 | 通过 | 本地截图（上一轮） |
| 长按/滑选不被吞 | 通过 | 慢速长按仍进入选择态（`已选 1 项`） |

### 12.2 内部存储显示 7.4 GB

原因：容量卡片对「当前目录」直接 `StatFs`。当路径是 `/storage`（tmpfs，7.4 GB）时就把 tmpfs 当内部存储了。
`/`、`/proc`、`/sys` 同理。

改法：新增 `StorageVolumes.resolve(path, sharedRoot)`，命中虚拟挂载点（`/storage`、`/storage/emulated`、
`/`、`/mnt…`、`/proc`、`/sys`、`/dev`、`/acct`、`/data_mirror` 及其子树）时改用 `/storage/emulated/0`
再取容量；`/data`、`/system`、SD 卡等真实分区仍显示各自容量。取不到时依次退到共享存储、`/data`。

| 项 | 结果 | 证据 |
| --- | --- | --- |
| `/storage` 下显示真实容量 | 通过 | MuMu 上从 `7.4 GB` 变为 `8.3 GB / 126 GB` |
| 真机安装新包 | 通过 | `adb install`，`lastUpdateTime=2026-10-25 13:20:54` |

### 13.3 `/storage/emulated` 打不开

现象：MT 能进 `/storage/emulated`（看到 0 / 999 / obb），VVFile 报「没有权限读取此目录」。

原因：FUSE 对应用隐藏了 `/storage/emulated` 这一层，返回的是 ENOENT；而 `FallbackFileSystem`
只在 `PathAccessDenied` 时回退 root，ENOENT 直接被当成「目录不存在」。

改法：

- `RootPaths` 增加判定：`/storage/emulated`、`/storage/self`、`/storage/emulated/<非 0 用户>`
  均视为 root-only（`/storage/emulated/0` 及其子目录仍走普通通道）；
- `FallbackFileSystem` 增加 `rootOnly` 谓词：ENOENT 且该路径被判定为 root-only 时，再走一次 su；
- 无 root 设备提示改为「系统限制访问该目录，需要 root 权限」，不再误报「路径不存在」。

底部留白，快捷命令 / 输入框贴在文字下方而不是屏幕底部。

### 14.1 配色跟随主题

原来终端颜色是 6 个写死的深色常量 + 一张写死的 ANSI 表。改成 `TerminalPalette`：

- `background / surface / divider / foreground / muted / accent` 六个角色，深/浅两套；
- ANSI 16 色也分深/浅两张表（浅色用 VS Code Light+ 风格，深底浅底都清晰）；
- 通过 `staticCompositionLocalOf` 下发，子组件只读 `LocalTerminalPalette.current`；
- 明暗判断用 `MaterialTheme.colorScheme.surface.luminance() < 0.5f`，与主题模式（跟随系统/深色/浅色/纯黑）天然一致。

快捷命令 chip 显式给 `assistChipColors(containerColor = palette.surface, labelColor = palette.foreground)`，
不再依赖默认配色在深色终端背景上的对比度。

| --- | --- | --- |
| 浅色主题终端为白底深字 | 通过 | 本地截图 |
| 浅色下执行命令可读 | 通过 | 点快捷命令 `pwd` → 输出 `/` |
| 深色主题仍是黑底 | 通过 | 本地截图 |
| 快捷命令 chip 可读 | 通过 | 两个主题下 chip 均为浅底/深底 + 对应前景色 |

### 14.2 输出区不铺满

根因：`Modifier.weight(1f)` 被传进 `TerminalOutput` 后挂在了**里面的 LazyColumn** 上，
而 LazyColumn 的父节点是 `SelectionContainer`，不是 Column，`weight` 被忽略 → 输出区按内容高度测量，
底下留白。

改法：`weight` 挂到 `SelectionContainer`（Column 的直接子节点），LazyColumn 用 `fillMaxSize()`。
顺带修好了「快捷命令 / 输入框不贴底」的观感。单测 187 全绿；Release 已装到真机（14:21:33）。

### 25.5 修正：菜单「清空」原先只重绘不清屏

**现象**：`ls` 之后点「清空」，屏幕闪一下但内容不变；而手打 `clear` 有效。

**原因**：`清空` 当时调的是 `TerminalSession.reset()`，它只重置解析器/边距/颜色等状态
（见 `TerminalEmulator.reset()`，里面**没有**清缓冲的动作），所以只有一次重绘。

**不能直接用「清仿真器缓冲」修**：mksh 的行编辑器自己记着光标列，偷偷把光标移回
`(0,0)` 会让它下一次补全/退格/重绘按错的列算位置，屏幕上出现错位字符。

**改法**：让 shell 自己清屏，和 `clear` 走同一条路径。

1. `$ENV` 启动脚本里补 `clear() { printf '\033[H\033[2J\033[3J'; }`
   —— 顺带解决部分机型没有 `clear` 二进制的问题，并清掉回滚区；
2. `清空` = 先发 `^U`（kill line，丢掉正在输入的那半行，且不像 `^C` 那样刷掉 tty
   输入队列）→ 60ms 后发 `clear` + 回车；
3. 会话已结束时没有 shell 可指挥，退化为直接把同一串清屏序列喂给仿真器。

| 项 | 结果 | 证据 |
| --- | --- | --- |
| `ls /data` + 半截命令后点「清空」→ 屏幕全空、只剩一条新提示符，半截命令未被执行 | 通过 | 本地截图、本地截图 |
| 清空后继续输入/退格：`echo ABC` → 三次退格 → `XYZ` 显示为 `echo XYZ`，无错位字符 | 通过 | 本地截图 |

## 26. 编辑器大文件改造 + 终端输入行换行的说明（2026-10-25 MuMu 验证）

### 26.1 编辑器：17.9 MB 小说打开 6 秒后可能被系统杀掉

**现象**：打开 1 MB 以上的 txt，转圈很久，随后闪退。

**实测复现**（MuMu / Android 15，use `C:\Users\19256\Downloads\斗破苍穹.txt`，17.9 MB）：
旧实现走「> 5 MB 只读预览」，读前 2 MB = 760,736 字符，全部塞进一个 `BasicTextField`：

| 指标 | 改造前 |
| --- | --- |
| 打开耗时 | 约 6–8 s，期间 InputDispatcher 连续报 `dropping inconsistent event`（主线程被排版占满） |
| 一次滑动 | 3.4 s |
| Native heap | 69 MB |

另外 `fieldValue` 用了 `rememberSaveable(TextFieldValue.Saver)`，把整篇文本写进 saved state Bundle，
旋转/切后台时会 `TransactionTooLargeException`——这也是"直接崩溃"的来源之一。

**改法**：

1. **按行虚拟化的只读查看器** `LargeTextReader`：
   `LineIndex` 只存每行起始偏移（173,988 行 ≈ 680 KB 的 int 数组），正文仍只有一份；
   `LazyColumn` 一行一个 item，只排版屏幕上那几十行。
2. **`fieldValue` 不再 saveable**（`remember`），正文由 ViewModel 持有，旋转后重新灌入。
3. **状态栏不再每次重组都 `substring + count`**（那是 O(全文)），查看器模式改用可见行号。
4. 网关拆成两个门槛：`MAX_EDITABLE_BYTES = 5 MB`（超过只读）、`MAX_LOAD_BYTES = 16 MB`
   （超过才截断）。原先 17.9 MB 只能看 2 MB，现在能看 16 MB。
5. 查看器补了：行号、可拖动进度条、「跳转行」对话框、`SelectionContainer` 选中复制。

**改造后**（同一个文件）：

| 指标 | 改造后 | 证据 |
| --- | --- | --- |
| 打开耗时 | < 1 s（tap → 首帧 750 ms，含 adb 往返） | 本地截图 |
| 一次滑动 | 即时，状态栏行号实时变化 | 本地截图 |
| 跳转到第 120000 行 | 即时 | 本地截图 |
| Native heap | 11 MB | `dumpsys meminfo` |
| 顶部提示 | 「大文件 · 只读分行预览 / 173988 行（只载入了前 16 MB）」 | 本地截图 |
| 状态栏 | 「编码：UTF-8 只读 · 行 1 / 173988 · 6097427 字符」 | 本地截图 |

### 26.2 终端：长输入行不换行是 mksh 的行为，不是没做处理

**现象**：输入很长的命令时，提示符和前半截被"吃掉"，只剩尾部一行 + 右边一个 `<`。

**定性**：这是 mksh 行编辑器的横向滚动（ksh 系传统），**不是**终端没实现换行。

- 输出换行是正常的：`ls` 长输出、报错文案、回车后的命令回显都会正确折行并有回滚
  —— 见 本地截图（第 2–5 行是 54 列满宽折行）
- 输入行是 mksh 自己画的：它只维护一行显示，超出宽度就把左侧滚出屏幕并在右边界打 `<`
- **已排除"我们的 PS1 太长导致误判"**：把 PS1 改成 2 个字符的 `$ ` 后再输 180 个字符，
  仍然是单行横向滚动 —— 见 本地截图
- `KSH_VERSION` = `@(#)MIRBSD KSH R59 2020/10/31 android`，系统自带版本

**结论**：与 Termux 同源同行为。要让输入行像 MT 那样换行，只有两条路，都属于新需求：

1. 内置别的 shell（bash/zsh 的行编辑器会换行）——Android 没有，且 targetSdk ≥ 29 的
   W^X 禁止 exec 应用私有目录里的二进制（`jniLibs` 解压后同样是 `/data/app/...`），
   所以不能像 Termux 那样塞一个 bash 进去；
2. 自己做行编辑器（不再让 shell 画提示符和回显）—— 相当于重写终端交互层，
   而且和 `vi`/`top` 这类接管 stdin 的程序冲突。

先把结论落到文档，等确认要不要走第 2 条。

MT 的批量重命名是一个 DSL：`{P}` 前缀、`{S}` 后缀、`{T}` 修改时间、`{E}` EXIF 时间、
`{N}` 序号、`{zN}` 补零序号，再加查找替换和正则开关，光说明文字就有八行。
实际用到的场景几乎只有两种：**加序号**、**改掉名字里的一段**。

所以只做两个模式，一个输入框 + 实时预览：

- **序号**：`#` 是序号的占位符，`##`/`###` 指定补零位数；**留空 = 原名 + 序号**
  （这就是 MT 默认 `{P}{S}{I}` 的效果，但不用背语法）
- **查找替换**：只作用于主名，扩展名不动，区分大小写，全部替换

实测（本地截图 → 本地截图）：

```
输入 test_# →  a.mp3  → test_01.mp3
               a.mp4  → test_02.mp4
               …
              新建文本-20261025-1847.txt → test_14.txt
应用后 ls：test_01.mp3 … test_14.txt，14 项全对，扩展名全部保留
```

校验（命中即不能点「应用」，预览里标红）：

| 问题 | 判定 |
| --- | --- |
| 名称为空 | result 全空白 |
| 非法字符 | 复用 `PathUtils.isValidFileName`（`/ \ : * ? " < > |`、控制字符、`.`/`..`） |
| 过长 | UTF-8 字节数 > 255（ext4/FUSE 上限） |
| 批内重名 | 批内结果重复 |
| 目录内已有同名 | 与未参与本批的条目重名 |

查找替换模式的空操作会被标成「未改动」，此时「将改动 0 项」且「应用」不可点
（本地截图、本地截图）。

**批内互换**（a→b 且 b→a）在 ViewModel 里做两阶段：先全批改成 `.vvrename_<i>.tmp`，
再落到目标名，避免互相覆盖。

| --- | --- |

### 30.3 到根目录后按返回/侧滑：什么都不做

以前 `BackHandler` 的 `enabled` 是「有选择态 / 抽屉开着 / 还能往上」，到 `/` 时三个都不成立，

```kotlin
BackHandler(enabled = true) {

        selectionActive -> clearSelection
        drawerState.isOpen -> close
        canNavigateUp -> navigateUp
        else -> Unit   // 根目录：吃掉，不退出
    }
}
```

> 想退出应用就上滑回桌面或用最近任务；这是「一滑就退」和「退不出去」之间的取舍，按需求取后者。

## 32. 列表缩略图（图片/视频预览 + 缓存，2026-10-27 MuMu 验证）

### 32.1 要解决的问题

MT 的列表里图片和视频是看得见内容的，VVFile 之前所有行都是一个分类图标——
在一个装满截图的目录里，`a.png` / `b.png` 长得一模一样，只能靠读文件名找东西。
需求就一句：**图片视频显示缩略图，缓存住，没加载出来就保持现在的图标**。

### 32.2 实现

新增 `core/thumb/`，分两层：`ThumbnailMath` 是纯函数（采样率、目标尺寸、缓存键），
`Thumbnails` 是 Android 侧的解码 + 缓存。

```kotlin
// Thumbnails.load 的取图顺序：内存 → 磁盘 → 现解码
val key = ThumbnailMath.cacheKey(path, size, lastModified)   // sha1(路径|大小|mtime)
memory.get(key)?.let { return it }
if (failed.contains(key)) return null                        // 坏图不再反复重试
return withContext(Dispatchers.IO) {
    gate.withPermit {          // Semaphore(3)：最多同时解 3 张
        memory.get(key)?.let { return@withPermit it }        // 排队期间别人可能已经解好
        readFromDisk(key)?.let { memory.put(key, it); return@withPermit it }
        val decoded = decode(File(path), isVideo)
            ?: run { rememberFailure(key); return@withPermit null }
        memory.put(key, decoded); writeToDisk(key, decoded); decoded
    }
}
```

界面上 `FileRow` 换成一个 32dp 的固定图标位（图标 20dp 居中、缩略图 30dp）：

```kotlin
val bitmap by produceState(
    initialValue = Thumbnails.peek(entry.path, entry.size, entry.lastModified),
    entry.path, entry.size, entry.lastModified, isVideo,
) {
    if (value != null) return@produceState
    delay(if (isVideo) VIDEO_SETTLE_MS else IMAGE_SETTLE_MS)   // 45 / 90ms，一闪而过的行不解码
    value = Thumbnails.load(entry.path, entry.size, entry.lastModified, isVideo)
}
```

要点：

| 关心的事 | 做法 |
| --- | --- |
| 没加载出来/失败 | `value` 为 null → 原分类图标，不出现灰块、不出现位移 |
| 快速滑动 | 先 `delay` 再解；行滑出屏幕 → `produceState` 协程取消，排队请求作废 |
| 长截图 | `inSampleSize` 同时看宽高：4000x100 保持原始宽度，只按长边算会压成 3 像素高 |
| 大图内存 | 采样率只取 2 的幂，把长边降到 128 的 1~2 倍；像素超 200 万继续降 |
| 同名文件被覆盖 | 缓存键带 `size` 和 `lastModified`，自动换图 |
| 视频取帧 | `MediaMetadataRetriever.getFrameAtTime(-1)`，返回空再退到 `0` 秒 |
| 透明图 | 磁盘存 PNG（不是 JPEG），透明区域露出底色 |
| 压缩包内条目 | `showThumbnail = false`：包内文件还没落盘，没有可读的源文件 |

### 32.3 缓存

- 内存：`LruCache`，容量 = 堆的 1/8（夹在 8–32 MB），`sizeOf` 用 `Bitmap.byteCount`
- 磁盘：`cacheDir/thumbs/<sha1>.png`，上限 64 MB，每写 32 张清一次，超了按 mtime
  从旧删到 48 MB（不每张都 `listFiles`，避免为省空间反而费性能）
- 启动时后台再清一次，防止上次进程留下的缓存已经超限

## 33. 文件类型图标（本地 Qwen-Image 生成，17 类，2026-10-27 MuMu 验证）

### 33.1 需求

- 用**本地跑的 qwen 模型**出图标，常用文件类型都要覆盖，风格统一
- 透明背景，提示词里带 `This is an RGBA image with transparency`
- 用户给的参考样式：白纸 + 黑描边 + 左下角彩色角标里写 `CPP`，

### 33.2 迭代过程（两版被否，第三版采用）

| 版本 | 长什么样 | 结论 |
| --- | --- | --- |
| v1 | 彩色卡片 + 白色象形图（山/音符/拉链/`</>`） | 没有类型文字，不符合参考样式 |
| v2 | 白纸 + 黑描边 + 左下角角标写类型 | 纸全是白的，一列里看着一模一样，被否 |
| v3 | **淡彩纸面 + 深色象形图 + 大号角标** | 采用：颜色、图形、文字三层区分 |

v2 的问题是真实存在的：`FileRow` 里一屏十几行，全白纸只有角标那点颜色不同，
远看就是一条白线。v3 把纸面按类型上淡彩，象形图和角标用同色系的饱和色，
角标再放大到「宽度过半、高度过五分之一」，28dp 下字虽然糊，但色块和图形认得出来。

### 33.3 生成链路

模型都在 `C:\Tools\ComfyUI`，脚本在 [design/icons](../../design/icons/README.md)：

```
unet   Qwen-Image-2.1-Turbo-AD-Q5_K.gguf        UnetLoaderGGUF
clip   qwen3vl_8b_int8_convrot.safetensors      CLIPLoader, type=qwen_image, device=cpu
vae    qwen_image_2.1_vae_bf16.safetensors
采样   euler + ManualSigmas 1.0 → 0（8 步，Turbo 蒸馏，不用 CFG / LoRA）
尺寸   1024×1024，每张约 70 秒（RTX 3060 Ti 8G，文本编码器放 CPU）
```

`gen.py` 走 ComfyUI 的 `/prompt` HTTP 接口（不是开界面点），生成完自动把输出拷到
`design/icons/raw/<类型>/`；`build.py` 再统一裁边、补描边、缩到 128px 写进
`app/src/main/res/drawable-nodpi/vvfile_ic_*.png`。

### 33.4 透明背景

提示词第一句固定 `This is an RGBA image with transparency.`，Qwen-Image 2.1 直接吐
4 通道 PNG（透明区 alpha=0）。实测每张的 alpha 分布：约 40–70% 完全透明、
边缘有 1~4 的过渡像素，没有出现「画一个棋盘格当透明」的情况。

收尾两件事：

- `alpha<10` 归零、`alpha>250` 归 255，去掉模型留下的毛边
- 缩到 128px 走**预乘 alpha**（PIL 的 `RGBa`），否则半透明边缘会把背景色混进图标，
  深色主题下能看到一圈脏边

### 33.5 风格统一怎么保证

同一段 `STYLE` 提示词逐字复用，只有「类型文字 / 纸面色 / 主色 / 象形图」四个变量：

- 竖版纸、右上角折角、纸的四个角半径一致
- 上半部分一个深色象形图（40% 纸宽）
- 左下角大角标压在纸角上，粗体大写文字（2026-10-27 起改成白色，见 §36）
- 不允许出现别的文字、投影、背景板

生成出来的图**描边时有时无**（同一个提示词、不同种子差别很大），
所以 `build.py` 统一在剪影外补一圈 18px 黑描边（1024 原图，折到 128px 约 2px），
17 张的线宽因此完全一致。

另外统一了取图规则：每个类型生成后按 `picks.json` 挑，缺省用最后一张。

## 40. 目录位置记忆（2026-10-27 MuMu 验证）

原来的行为是「换个目录再回来永远从顶部开始」：路径一变就把列表强滚到第 0 行。
在几百个条目的目录里翻到一半、去别的目录看一眼再回来，还得重新找位置。

- 新增 `ScrollMemory`：按「窗格 + 目录」记下落点的首行索引与视口偏移，
  两个窗格各留一份，超过 64 个目录淘汰最久没访问的那个
- 落点在离开目录那一刻存（`DisposableEffect` 的 `onDispose`）。不挂滚动监听是刻意的：
  切目录时列表先被清空，挂着监听会在 `onDispose` 之前把 0 写进旧目录的记录里

  同一目录刷新、复制完成后的列表重载都会改条目数，不该把人又拽回原来那行
- 停在顶部（0,0）不记：省得白占名额，回顶部的目录下次进来还是顶部
- 排序 / 过滤 / 显示隐藏文件变化时整片作废并回到顶部：行号对不上原来那条了
- 落点存在 ViewModel 里，转屏、进编辑器再返回都还在；进程被杀就清空

## 41. root 目录里的文件能读能改（2026-10-27 KernelSU 真机 / MuMu 验证）

反馈：KernelSU 授权后 `/data/adb` 能进、目录能删，点开文件却提示「无法打开文件 / 没有权限读取此文件」。

**原因是两条路权限不一样**：浏览（`ls`）、删除（`rm`）都经 `su -c` 执行，读文件内容走的却是
应用自己 uid 的 `Files.newInputStream` / `ZipFile` / `BitmapFactory`。`/data/adb` 是 0700 root:root，
应用自己当然读不到——于是「能列、能删、打不开」。这个问题不只是文本编辑器，
图片、视频、音频、压缩包、「打开方式」都是同样的根因。

**做法**

- 新增 `RootFileChannel` 接口 + `SuRootFileChannel`：
  - `stat -c '%F|%s|%Y'` 取类型/大小/修改时间
  - `cat -- path` **按字节流式读**，读满上限直接 `destroy()`，不把大文件拉进内存
  - `writeAll`：先落到应用缓存，再让 root 用 `cat > 目标` 覆盖（保留原 inode、权限位与属主）
  - `copyTo`：`cp` 到缓存后 `chmod 0664`，否则 root 复制出来的 0600 文件应用自己还是读不了
- `EditorFileGateway`：直接通道抛 `AccessDenied`/`SecurityException` 时改走 root 通道，
  目录判定、大小上限（5 MB 只读 / 16 MB 截断）、编码识别逻辑全部复用；
  保存同理回退，写入前用 root `stat` 复核大小，超过 5 MB 仍然拒绝
- `RootStaging`：图片/视频/音频/压缩包/「打开方式」只认路径，先把文件复制到
  `cache/root-stage/`（文件名带大小+修改时间，源变了换新；最多 24 份，LRU 淘汰），
  再交给解码器/播放器/`ZipFile`
- 只有「应用自己读得到」的路径才走 root：`canRead()` 为真的文件行为完全不变；
  root 策略为「禁用」时仍报原来那句「没有权限」

**验证**

- 单测（15 条）：`EditorRootFallbackTest`（回退读取、root 关闭时保留原文案、stat 失败、
  目录拒绝、超大文件截断且只读、保存回退、超过 5 MB 拒绝覆盖）、
  `RootStagingTest`（缓存命中只复制一次、可读文件不落地、目录/无元数据/复制失败返回 null、
  大小变化使旧副本失效）
- MuMu（1080×1920，KernelSU 授权后）：`/data/local/rootonly/secret.conf`（0600 root:root，
  19 B）列表可见 → 点开直接进入编辑器并显示两行内容；抽屉徽标显示「root 可用」
- 真机（KernelSU，用户实测）：`/data/adb` 下文件可打开、可新建、可编辑保存

## 44. 带密码的压缩包（2026-10-27 MuMu 验证）

Android 14+ 的 `java.util.zip.ZipFile` **打不开**带加密条目的 ZIP，直接抛
`invalid CEN header (encrypted entry)`——之前的表现是压缩包浏览页停在一句英文报错，
「解压」则提示「无法读取压缩包」，都对用户没有意义。

- 新增 `ZipCentralDirectory`：自己解析 EOCD + 中央目录，读通用标志位 bit0（加密），
  顺带拿到条目名、未压缩大小和 DOS 时间。Zip64 或结构异常返回 null，退回 `ZipFile`
- `ArchiveIndex.read` 先读中央目录；`ZipFile` 抛错且有加密条目时，用中央目录的列表顶上，
  于是**加密包也能进包内浏览**，条目名前挂 🔒
- 点加密条目 → 「此条目已加密，暂不支持输入密码」；解出失败（损坏/软链接）也有提示
- 「解压」在冲突探测之前就判加密，直接提示同一句；`LocalFileOperator.runUnzip` 里
  `ZipFile` 打开失败且确有加密条目时，也转成这条提示

验证（MuMu 1080×1920）：用 ZipCrypto 生成 `encrypted.zip`（`secret.txt` + `docs/note.md`，
口令 123456，Python `zipfile` 确认 `flag_bits=1` 且无密码拒绝读取）：

- 点开：列表显示 `docs 🔒`、`secret.txt 🔒 27 B`（不再出现英文 CEN 报错）
- 点 `secret.txt`：toast「此条目已加密，暂不支持输入密码」
- 长按 → 解压：toast「压缩包已加密，暂不支持输入密码」
- 单测 6 条：普通包无加密项、标记后可读出、非 ZIP/空文件不抛异常、
  中央目录条目名与大小、加密标记跟着条目走

## 45. 加密压缩包能解开了（2026-10-27 MuMu 验证）

§44 那会儿只能认出「这包有密码」，解不开。这一节把它做完：**ZIP 的两种加密自己写，
7z 交给 `commons-compress` + `xz`**。

7-Zip 的 C 源码在本机，但它的 LZMA / LZMA2 解码器是几千行状态机，抄成 Kotlin 再调
bug 不划算；ZIP 的两套加密（ZipCrypto、WinZip AES）规则清楚、代码量小，自己写反而
可控——而且这样才能在「打开阶段」就判出密码对不对，而不是读一半才抛 CRC 错。

### 45.1 三种加密各走哪条路

| 加密方式 | 参数在哪 | 算法 | 代码 |
| --- | --- | --- | --- |
| ZipCrypto（传统 ZIP 加密） | 数据区前 12 字节加密头 | 三把 32 位滚动密钥，头的最后一字节 = CRC 高字节 | `core/archive/ZipCrypto.kt` |
| WinZip AES（AE-1 / AE-2） | 中央目录额外字段 `0x9901` | PBKDF2-HMAC-SHA1 1000 轮派生 AES/HMAC 密钥 + 2 字节校验值；小端计数器 AES-CTR；尾部 10 字节 HMAC-SHA1 | `core/archive/WinZipAes.kt` |
| 7z AES-256-CBC | 7z 容器头 | `commons-compress` 解容器、`xz` 解 LZMA/LZMA2 | `core/archive/SevenZipArchive.kt` |

- `ZipEntryReader` 负责定位数据区（本地文件头 + 限长流，防止越界读到下一条），
  解密后再按**真实压缩方式**解压（AES 条目的方式字段写的是 99，真实值在额外字段里），
  读完做 CRC 校验；AE-2 不写 CRC，只认 HMAC
- 密码框三处共用（打开包 / 点加密条目 / 长按解压）：`ArchivePasswordDialog`；
  密码按包路径记在内存里（LRU 16 条，**不落盘**），解开一条就算验过，后续条目不再追问
- 错误口径：没密码 → 「压缩包需要密码」；密码错 → 「密码不正确」留在框里；
  7z 没有校验字节，只能说「密码不正确或压缩包已损坏」
- 整包解压（`LocalFileOperator`）把密码一路带到条目级，ZIP 与 7z 共用同一套
  Zip Slip 校验 + 冲突策略 + 进度；错密码在第一条就停，不会刷一屏失败项

### 45.2 两个把自己坑到的细节

1. **ZipCrypto 的密钥流必须跨加密头**：解完 12 字节头要接着用同一份密钥状态解数据，
   第一版解完头就 `new` 了一个新实例，症状是「密码明明对，CRC 全错」。
   现在 `ZipCrypto.openHeader()` 把实例和校验字节一起返回。
2. **AES 的盐不是密钥长度**：盐长 = 密钥长的一半（AES-128/192/256 → 8/12/16）。
   一开始直接拿密钥长度当盐长度，多吃了 16 字节，PBKDF2 出来的 2 字节校验值必然不匹配，
   表现同样是「正确密码被判错」。
